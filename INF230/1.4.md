# 1.4 Ontologiutvikling


**Ontology development** = designing an ontology that represents the concepts and relationships needed for a particular **knowledge domain**.

Two important approaches:

- **Bottom-up** → start from concrete information/examples and generalize.
    
- **Top-down** → start from general/foundational concepts and specialize.
    

---

## 1. Bottom-up ontology development

Start with the **actual domain/data** you want to represent.

Example from the slides:

> “Today it is 30°C in Saloniki.”

Represent this using **triples**:

```text
x₀ → is a → TemperatureMeasurement
x₀ → hasLocation → Saloniki
x₀ → hasMeasurementValue → 30°C
x₀ → hasMeasurementDate → 2025-07-05
```

Then define the ontology concepts:

```text
Saloniki → City
City → subclass of → Location

30°C → TemperatureValue
TemperatureValue → subclass of → QuantityValue
```

### Key point

The **TBox** contains the general concepts/classes and relationships.

The **ABox** contains the actual individuals/facts.

```text
TBox = categories / concepts / schema
ABox = instances / facts / state of affairs
```

---

## 2. What makes an ontology “good”?

The slides use an example involving lions.

A **good ontology** should represent the domain accurately and with enough constraints.

Example:

```text
Every lion has exactly 4 legs.
Every lion is a carnivore.
Every lion eats at least some impala.
```

### Less good ontology

Statements may all be technically true, but allow **too many possible models**.

Example:

```text
Every lion has at least some legs.
Every lion is a carnivore.
Every lion eats at least some impala.
```

This could allow lions with 2, 5, or 100 legs.

### Bad ontology

Does not contain everything required.

Example:

```text
Every lion eats at least some impala.
```

Important information is missing.

### Worse ontology

Contains **out-of-domain or incorrect knowledge**.

Example:

```text
Every painting depicts at least some bear.
```

when the domain concerns African wildlife.

### Remember

```text
Good       → represents intended domain accurately
Less good  → too weak / allows unintended models
Bad        → missing required knowledge
Worse      → includes incorrect/out-of-domain knowledge
```

# Competency Questions

## What is a competency question?

A **competency question (CQ)** is a question the ontology/data infrastructure must be able to answer.

It is:

```text
requirement → expressed as a natural-language question
```

Example:

> What hazardous substances does a product contain?

> What is the environmental impact of a product during its lifecycle?

The ontology is successful when it contains enough information/structure to answer the required questions.

---

## CQ → SPARQL

A competency question can be translated into a **SPARQL query**.

Example:

> “For a DMPP instance: identify the material and the batch/delivery unit.”

The ontology must contain the necessary:

```text
classes
+
properties
+
relationships
```

so that the question can be expressed as SPARQL.

### Important exam idea

> **A CQ is a requirement for the ontology.**

A CQ is **covered** when the ontology allows the CQ to be expressed as a SPARQL query.

# Agile requirements analysis

Ontology requirements can also be gathered using **agile requirements analysis**.

Main idea:

```text
Talk to stakeholders
        ↓
Identify requirements
        ↓
Write user stories
        ↓
Group related stories into epics
```

### User story

Format:

```text
As a <persona>,
I want to <action>,
to achieve <aim>.
```

Example:

```text
As a researcher,
I want to find all measurements,
to analyse the experiment.
```

### INVEST

Good user stories are:

```text
I = Independent
N = Negotiable
V = Valuable
E = Estimable
S = Small
T = Testable
```

### Epic

A larger/coarse-grained objective containing multiple user stories.

```text
Epic
 ├── User story
 ├── User story
 └── User story
```

### Persona

An **imaginary representation of a user role**.

It represents a group of users rather than necessarily one real person.

# Reification

## What is reification?

**Reification** = turning a relationship/statement into something that can itself have properties.

Normal triple:

```text
Shakespeare → wrote → Hamlet
```

But what if we want to say:

```text
Shakespeare wrote Hamlet
in 1601
according to source X
with probability 90%
```

We need to represent the **statement itself** as an entity.

Conceptually:

```text
Statement₁
 ├── subject → Shakespeare
 ├── predicate → wrote
 └── object → Hamlet

Statement₁ → publicationDate → 1601
```

### Why?

Because a normal binary/ternary relation does not directly give us a place to attach metadata about the relationship.

### Remember

> **Reification = making a relationship/statement into an object so we can describe it.**

# Ontology evaluation

## OOPS!

**OOPS!** = OntOlogy Pitfall Scanner!

Used to detect problems in ontology structure/implementation.

Examples of checks:

- Are domains and ranges specified?
    
- Is the ontology namespace properly defined?
    
- Are there structural modelling problems?
    

---

## FOOPS!

**FOOPS!** checks whether an ontology has been published in a **FAIR** way.

```text
F = Findable
A = Accessible
I = Interoperable
R = Reusable
```

### Difference

```text
OOPS!  → ontology design / modelling pitfalls
FOOPS! → FAIRness of the ontology
```

---

# Reuse existing ontologies

Before creating a new concept, check whether an existing ontology already provides it.

Example from the slides:

```text
Product / batch
→ reuse CEON / OntoDESIDE

Duration
→ reuse schema.org
```

Advantages:

- less duplication
    
- better interoperability
    
- easier integration with other datasets
    
- shared semantics
    

### Important principle

> **Don't reinvent an ontology when an appropriate existing ontology can be reused.**

# Ontology hierarchy

Typical semantic architecture:

```text
Foundational / Top-level
        ↓
Middle-level
        ↓
Domain-level
        ↓
Application-level
```

### Foundational ontology

Most abstract level.

Describes very general concepts about **what exists and how things relate**.

### Domain ontology

More specific ontology for a particular knowledge domain.

Example:

```text
Foundational ontology
        ↓
Materials
        ↓
Chemistry
        ↓
Specific application
```
